# 📱 実機テスト（iPhone 18 Pro Max）

[READMEへ戻る](../README.md) · [English](en/real-device-test.md)

2026-09-29に、iPhone 18 Pro Maxの実機で、帯域の記録が入った公開版（`090648f`）を確かめました。この資料の値は、そのとき書き出したCSVから採ったものです。CSVそのものは筆者の部屋で採った記録なので、リポジトリーには入れていません。どの環境でどこまで確かめたかの一覧は、[README](../README.md)の「ブラウザー対応状況」にあります。

## 使った端末と条件

| 項目 | 内容 |
|---|---|
| 記録した端末 | iPhone 18 Pro Max（1台）のSafari |
| 記録した版 | 公開版（GitHub Pages、main `090648f`）。帯域ありと`?bands=off`の両方で開いた |
| ログ間隔 | 1秒 |
| 音源 | PCにUSBでつないだスピーカー（FOSTEX PC200USB-HR）。PC側の出力は48000Hz／24bitで、PCの中でサンプルレートの変換は起きていない |
| 置き方 | 階段シーケンスでは、iPhoneの下端をスピーカーの正面10cm以内に置き、最後まで動かさなかった。扇風機・スピーカーのオン／オフも同じ場所に置いた（筆者の申告） |
| 部屋 | 扇風機・PCのファン・別室の洗濯機の音がある部屋。この資料で「静か」と書いた値は、これらの音を含む |
| 検証器 | 書き出したCSV（`090648f`で書き出したv3が8本と、`c7b6bad`で書き出したv2が1本）は、すべて[CSVの資料](csv.md)の「受け取ったCSVを検証する」の検証器を通った（v3は帯域ありの60行・`?bands=off`の114行・階段シーケンスの100行ほか、v2は86行） |

## 実機の関門：FFTを計算するときの有効サンプル率

帯域の値は、区間を集計するオーディオスレッドでFFTを計算して求めます。iPhoneで計算が間に合わなくなると、レンダークォンタム（128サンプルの塊）を落とし、その区間の`valid_ratio`が1.000を下回ります。同じ版を帯域ありと`?bands=off`（FFTを計算しない）で開き、画面をつけたまま記録して比べました。

| 項目 | 帯域あり | `?bands=off` |
|---|---|---|
| 記録した行 | 60行（約1分） | 114行（約2分） |
| `valid_ratio`が1.000未満の行 | 0／60 | 0／114 |
| `band_valid_ratio`が1.000未満の行 | 0／60 | （空欄） |
| 1行目の`valid_ratio` | 1.000 | 1.000 |
| 静かな行の`dbfs`の中央値 | -75.67 | -75.44 |
| 静かな行の超音波帯の中央値 | -101.74 | （空欄） |
| 静かな行の可聴帯の中央値 | -76.27 | （空欄） |
| `clip`が0でない行 | 0 | 0 |
| 叩いた行の`peak_dbfs` | -41.28・-49.60・-41.80 | -38.10・-38.90・-31.48 |

- ⭐**FFTを計算しても、この端末ではレンダークォンタムを落としていない。**帯域ありの60行・`?bands=off`の114行とも、`valid_ratio`は全行1.000だった。帯域の計算も、数えるはずのフレームをすべて数えた（`band_valid_ratio`も全行1.000）
- ⚠確かめたのは、画面をつけたままの1分と2分だけである。長時間の記録・画面ロック中・バックグラウンドでは確かめていない
- 静かな室内（スピーカーから離れた場所）の超音波帯は約-102dBFSで、全帯域（約-76dBFS）より約26dB低かった

## 叩いたときのクリップ

記録の途中で、マイクのあたりを軽く3回叩きました（上の表の最後の行）。`peak_dbfs`は-31〜-50dBFSで、上限の0dBFSまで30dB以上あり、クリップした行はありませんでした。叩いた音は超音波帯にも少し出ています（帯域ありのseq 17で-93.93dBFS、静かな行より約8dB上）。

`c7b6bad`の版で採った別の記録では、クリップが8区間・延べ385サンプル出ていました。そのときはマイクのあたりを叩くように触っていたので、軽く叩くよりも強い接触だったと考えられます。ただし、そのときのCSVは残っていないので、原因は確かめられていません。

## Safariが報告した測定条件

帯域ありの記録のヘッダーには、次の2行が出ました（`?bands=off`でも同じです）。

```
# processing=unknown:autoGainControl+noiseSuppression
# settingsRaw=echoCancellation:false;autoGainControl:unreported;noiseSuppression:unreported;sampleRate:48000;channelCount:unreported
```

- Safariの`getSettings()`は、音の加工の3項目のうち`echoCancellation`しか報告しなかった（`false`＝無効）。`autoGainControl`と`noiseSuppression`は報告されないので、`# processing=`は`unknown:autoGainControl+noiseSuppression`になる。WebKitのソースを読んで立てた見立てと同じ結果である
- そのため、AGCとノイズ抑制が切れていたかは、このCSVからは分からない。`channelCount`も報告されなかった
- 音声トラックのサンプルレートは48000Hzで、AudioContext（`# sampleRate=48000`）と同じだった。サンプルレートの変換がないので、[CSVの資料](csv.md)の「帯域の列」にある疑似マイクの例（音声トラック44.1kHz）のように、超音波帯の値が変換で下がることはない

## 階段シーケンス：18〜22kHzのトーンの記録

PCから1kHz・15〜22kHzのトーンを順に鳴らし（各5秒、あいだに2秒の静寂、全9段で約65秒）、iPhoneで記録しました。PC側のログに残る各段の開始時刻で、CSVの行と周波数を合わせています（iPhoneとPCの時計のずれは、音が届くまでの遅れを含めて約0.84秒でした）。各段の値は、トーンがまるごと入った4行の電力の平均です。単位はdBFS、静寂との差の単位はdBです。

| 周波数 | 行（`seq`） | 全帯域 | 超音波帯 | 静寂との差（超音波帯） | 可聴帯 |
|---|---|---|---|---|---|
| 静寂（前） | 0-16 | -73.72 | -92.99 | 0 | -74.21 |
| 1kHz | 19-22 | -37.50 | -93.61 | -0.62 | -37.50 |
| 15kHz | 26-29 | -58.55 | -93.85 | -0.86 | -58.57 |
| 16kHz | 33-36 | -66.46 | -93.87 | -0.88 | -66.54 |
| 17kHz | 40-43 | -58.69 | -93.88 | -0.89 | -58.71 |
| 18kHz | 47-50 | -63.24 | -64.37 | +28.61 | -69.75 |
| 19kHz | 54-57 | -60.08 | -60.23 | +32.75 | -75.14 |
| 20kHz | 61-64 | -51.73 | -51.75 | +41.24 | -75.24 |
| 21kHz | 68-71 | -59.83 | -59.97 | +33.01 | -75.27 |
| 22kHz | 75-78 | -74.66 | -91.74 | +1.25（直後の静寂とは+1.9） | -75.24 |
| 静寂（後） | 80-99 | — | -93.66（σ≈0.1dB） | — | — |

- ⭐**18〜21kHzは、超音波帯の値ではっきり記録できた。**静かなときより+29〜+41dB高い。19〜21kHzのあいだ、可聴帯の値は静寂とほぼ同じで、帯域の分け方どおりに入っている
- ⭐22kHzは、超音波帯の値でわずかに上がった。直後の静寂（-93.66、行ごとのばらつきσ≈0.1dB）より約+1.9dB高く、4行とも-91.7〜-91.8でそろっている。全帯域の値（-74.66）では静寂と区別できない
- 22kHzのトーンだけの強さに直すと約-96〜-98dBFSで（前後どちらの静寂を基準にするかで変わる。帯域の端で約2dB低く出るぶんを含む）、21kHz（-60.0）から約36〜38dB落ちている
- 36〜38dBのうち約2dBは、本ツールの側で低く読んだぶんである。22kHzは超音波帯の上端に乗るので、音の一部が帯域の外へ漏れる（[CSVの資料](csv.md)の「帯域の列」。21kHzは帯域の内側なので、このぶんはない）。残りの約34〜36dBが、音源から本ツールに届くまでのどこかで落ちている
- ⚠**22kHzで落ちている原因が音源側か受音側かは、分けられない。**PC側でサンプルレートの変換は起きていない（48000Hzどうし）ので、残りの約34〜36dBを落としているのはスピーカー（DAC・アンプ・ツイーター）かiPhone（マイク・AD変換のフィルター）のどちらかである。この構成では、どちらなのかを決められない
- 18kHzのトーンは、超音波帯（-64.37）と可聴帯（-69.75）の両方に入った。可聴帯から静寂のぶんを引くと-71.7で、超音波帯との差は約7.3dBになる。18,000Hzちょうどの音は、窓の漏れで超音波帯に5/6・可聴帯に1/6入るという計算（差7.0dB）と合った
- 帯域の列を設けているのは、この表の22kHzのように全帯域の値に埋もれる高い音を、分けて残すためである

## 画面で22kHzが見えなかった理由と、表示下限の既定

記録しているあいだ、22kHzでは画面の数字もグラフも動かないように見え、21kHzでは反応しました（筆者の記憶によります。CSVの値から考えても、同じ見え方になります）。CSVには+1.9dBの差が残っていたので、記録ではなく表示の問題です。

- 大きな数字とメーターは全帯域の値である。22kHzのトーンは暗騒音（全帯域で約-74dBFS）より20dB以上小さいので、全帯域の値はほとんど動かない
- 超音波帯の破線は-93.7から-91.7へ上がっていたが、記録した版（`090648f`）の表示下限の既定（-90dBFS）より下なので、グラフの下端に張り付いて見えなかった
- 21kHzでは超音波帯が-60まで上がったので、数字にも破線にも出た

帯域を計算するときの表示下限の既定は-110dBFS（`?bands=off`では-90dBFS）で、大きな数字のすぐ下に超音波帯の値を数字で出します（[機能の資料](features.md)の「超音波帯（18〜22kHz）の記録と表示」）。-110〜0dBFSの縦軸では、2dBの変化は高さの約2%にしかならないので、数dBの変化は数字で読んでください。⚠この表示は、実機ではまだ確かめていません。

## 扇風機とスピーカーのオン／オフ

階段シーケンスのあと、同じ場所（スピーカーの正面10cm）で扇風機とスピーカーの電源を切り替え、約30秒ずつ記録しました。値は行の中央値です（1行だけ飛び抜けた値に引っぱられないようにするため）。

| 条件 | 全帯域 | 可聴帯 | 超音波帯 |
|---|---|---|---|
| 扇風機オン・スピーカーオン（階段シーケンスの直後の静寂） | -74.68 | -75.24 | -93.67 |
| 扇風機オン・スピーカーオフ | -75.92 | -76.47 | -104.02 |
| 扇風機オフ・スピーカーオン | -79.67 | -79.84 | -105.05 |

- ⭐**扇風機は、全帯域を約3.8dB、可聴帯を約3.4dB上げる**（扇風機オン・スピーカーオフと、扇風機オフ・スピーカーオンの差。全帯域は-75.92と-79.67、可聴帯は-76.47と-79.84。スピーカーの寄与は小さいとみなした）
- ⚠**階段シーケンスの直後の超音波帯-93.7は、扇風機だけ・スピーカーだけ（どちらも-104〜-105）では説明がつかない。**扇風機を止めたまま、PCからスピーカーへ無音の音声が流れ続けている状態と、音源のページを閉じた状態も同じ場所で採ったが、超音波帯の中央値は-107.0と-106.0で、これでも説明がつかなかった
- 置き場所のわずかなずれ、端末の状態、その時間だけ鳴っていた部屋の音、扇風機とスピーカーを同時に入れたときだけ起きること、などの候補は残ったままで、原因は分かっていない
- この例では、帯域の値が平時より約10dB高い時間帯は見つけられたが、何の音かは分からなかった。条件を1つずつ変えて比べても、出どころを突き止められるとは限らない。[ユースケースの資料](use-cases.md)の「平時と比べる」は、この限界を前提に使う

## 実機で確かめていないこと

- Androidの実機（どの機種・ブラウザーも確かめていない）
- 実機での画面ロック中・バックグラウンドの挙動（とくにiOS Safariの`AudioContext`の扱い）
- 長時間の記録（確かめたのは、1分・2分の記録と、約100秒の階段シーケンスの記録まで）
- ほかのiPhone（確かめたのは1台だけで、機種やiOSの版が違うものは見ていない）
- 22kHzで落ちる原因が、音源側か受音側か（別の音源か別のマイクで同じシーケンスを採れば分けられる）
- 実機テストの版（`090648f`）より後に入れた画面（表示下限の既定-110dBFS・超音波帯の現在値・ボタンの配置）
- 日英の切り替え（デスクトップのChromiumでだけ確かめた）

## 実機テストのやり方

PCで1kHzと15〜22kHzのトーンを低いほうから順に鳴らし、スマートフォンで記録して、CSVの行と周波数を合わせます。1kHzと15〜17kHzは、スピーカーとマイクが動いていることの確かめで、知りたいのは18〜22kHzのどこで記録に残らなくなるかです。

1. 記録する端末（スマートフォン）で公開版を開き、ログ間隔を1秒にして「記録開始」を押す
2. 音を出す端末（PC）で、決まった周波数のトーンを順に鳴らせる音源を開く。まず1kHzを鳴らし、耳に痛くない大きさまで音量を絞る
3. 記録する端末をスピーカーの正面（10cm前後）に置き、最後まで動かさない。途中で動かすと、周波数ごとの値を比べられなくなる
4. 静寂を挟みながら、低い周波数から順に鳴らす（上の記録は1kHz・15〜22kHz、各5秒、あいだに2秒の静寂）。音源側で、各段を鳴らし始めた時刻を記録しておく
5. 終わったら記録を止めてCSVを書き出し、[CSVの資料](csv.md)の「受け取ったCSVを検証する」の検証器にかける
6. 音源側の時刻とCSVの`timestamp`（区間の終わり・UTC）で、どの行がどの周波数だったかを合わせる。端末どうしの時計のずれと音が届く遅れがあるので、トーンがまるごと入った行（段の最初と最後の行を除いた行）で比べる。超音波帯の値が静寂の行より高ければ、その周波数は記録に残っている

- ⚠15〜17kHzは多くの人に聞こえる。18kHz以上は聞こえないまま大きな音が出ていることがあるので、必ず音量を絞ってから始める。近くに子ども・動物がいる場所では行わない
- 音源側の出力のサンプルレート（44100Hzか48000Hzか）も記録しておく。44.1kHzで鳴らす機材には、変換器のフィルターの通過域がおよそ20kHzまでのものがあり、それより上が音源側で落ちると、受音側の限界と区別できなくなる

上の記録で音源に使ったページ（Tone Sweep）は、実機テストのために手元で作ったものです。後日、単体のツールとして公開する予定で、公開したらここにリンクを張ります。
